> **한 줄 요약**: (1) 추론이 0.5초 늦으면 성공률 90%→12%, 그런데 연구실 1080 Ti 의 실측 추론이 딱 0.56초다. (2) LoRA 2차는 망각을 되돌렸지만(태스크 1: 60%→100%) 전환은 32%→31% 로 그대로다. (3) 학습한 판정기는 후보를 전혀 못 골랐다(Q−V = 0.0003) — 후보 선택 방향의 상한을 오라클로 재고 있다. (4) **그 자리에서 전환하면 중단한 A 를 다시 해내는 비율이 0%** (23번 전부 시간 초과), 물체를 되돌린 경우만 62%.

## 알게 된 것

### 1. 0.5초 지연에 무너진다

![지연](../04_실습/05_libero/latency/results/latency.png)

| 지연 | RTC 끔 | RTC 켬 |
|---|---|---|
| 없음 | 90% | 75% |
| 0.25초 | 72% | 72% |
| **0.5초** | **12%** | **28%** (6 : 0, p≈0.03) |
| 1초 | 0% | 8% |

- 오래된 관측으로 만든 동작이 실제와 어긋나고, 새 동작이 올 때마다 방향이 튐
- **RTC 는 지연이 있을 때만 이득** — 어제 "RTC 는 손해"라고 한 결론은 **지연 없는 조건에 한정**된 것이었음. 논문 주장이 맞는 조건을 확인

### 2. 전환은 지연에서 더 어렵다

| 잡은 직후 전환 | 지연 없음 | 지연 0.5초 |
|---|---|---|
| flush | 27% | 10% (1.5초 멈춤) |
| keep | 30% | 13% |
| rtc | 30% | 7% |

- 성공률 절반 이하. flush 는 기다리며 **멈춰 서서** 자연스러움 제약에도 어긋남

### 3. ⚠️ 1080 Ti 실측 지연이 정확히 "무너지는 구간"이다

| 조건 | 1회 추론 | 20Hz 기준 |
|---|---|---|
| **GPU 단독** | **560ms** | **11.2 스텝 ≈ 0.56초** |
| GPU 공유 (평가 2개와 함께) | 1281ms | 약 26 스텝 |

**실측 0.56초는 위 표에서 성공률이 90% → 12% 로 무너지는 0.5초 구간과 일치합니다.**

| | 지금까지 측정 (동기 실행) | 실제 지연 0.5초 |
|---|---|---|
| 태스크 성공률 | 90% | **12%** (RTC 28%) |
| 잡은 직후 전환 | 27~30% | **7~13%** |

- 지금까지의 모든 수치는 **낙관적**이다. 실물 PiPER 에 이 GPU 로 올리면 오른쪽 열이 현실
- **저사양 대응이 선택이 아니라 필수**: RTC(12→28%), `n_action_steps` 늘려 추론 횟수 줄이기, 비동기 추론, 입력 해상도 줄이기
- 시뮬 1스텝은 15.6ms 라 실시간(50ms)보다 빠름 → 병목은 순수하게 모델 추론

### 4. LoRA 2차 — 망각은 고쳤는데 전환은 그대로

![버전 비교](../04_실습/05_libero/lora_v2/img/lora_versions.png)

| | 원본 | LoRA 1차 | **LoRA 2차** |
|---|---|---|---|
| 전환(flush) B 성공 | 32% | 32% | **31%** (짝 비교 7:9, p≈0.80) |
| 교란 없는 기본 성능 (7·1·5 평균) | 86.7% | 73.3% ⬇ | **90.0%** ✅ |
| 태스크 1 교란 없음 | 100% | 60% ⬇ | **100%** ✅ |
| 손목 20° (태스크 7) | 60% | 70% | **90%** ✅ |
| 성공 시 우회 비율 (1=곧게) | 1.52 | 1.45 | **1.42** |

- **1차의 망각을 되돌렸습니다.** rehearsal(정상 궤적 추가) + r 16→8 + 지시문 균형 샘플링. [LoRA 망각 논문](../02_논문노트/LoRA-망각.md)의 처방이 그대로 통했습니다
- **그런데 전환은 1%p 도 안 움직였습니다.** 데이터를 4배 늘리고 hindsight 를 넣어도 마찬가지
- **왜**: 우리 데이터는 "이미 성공하는 것"의 재현입니다. 실패하는 쌍(1→5, 2→5)의 **정답 동작이 데이터에 없습니다.** [Q-Planning](../02_논문노트/Q-Planning.md)이 말한 filtered SFT 의 한계
- 게다가 [9/17 가설 검증](../04_실습/05_libero/hypothesis_check/README.md)에서 전환 실패가 **자세 때문이 아니라는 것**을 확인했으니, "교란 자세에서 회복"을 가르쳐도 전환은 안 늘어나는 게 당연합니다

### 5. 학습한 판정기는 후보를 못 골랐다 (결정적인 음성 결과)

전환 이후의 모든 결정 11,563개(209 에피소드)로 "이 결정 이후 B 가 성공할까"를 맞히게 학습시켰습니다.

| 입력 | AUC |
|---|---|
| V — 상태만 (이미지·지시 특징 + 로봇 상태) | 0.9318 |
| **Q — 상태 + 실행할 동작 10스텝** | **0.9321** |
| 상태 + 동작 (다른 구조) | 0.9406 |

**Q − V = 0.0003.** 동작을 알려줘도 예측이 나아지지 않았습니다. 즉 **"어떤 동작을 고르든 결과는 상태에서 이미 정해져 있다"**는 뜻입니다.

- 이게 [9/17 의 bon 실패](../04_실습/05_libero/training_free/README.md)(34% vs flush 32%, p≈0.82)를 설명합니다. 고를 만한 차이가 없었던 겁니다
- [V-GPS](../02_논문노트/V-GPS.md)·[RoboMonkey](../02_논문노트/RoboMonkey.md) 가 보고한 이득이 우리 조건에서는 재현되지 않았습니다
- **단 한 가지 빠져나갈 구멍**: 우리 데이터는 각 상태에서 **실제로 실행한 동작 하나**만 봤습니다. 실행하지 않은 다른 후보가 성공했을지는 모릅니다
- → 그래서 **오라클 Best-of-N**: 시뮬 상태를 저장하고(`get_sim_state`) 노이즈만 바꿔 8번 다시 굴립니다. 하나라도 성공하면 "좋은 후보는 존재한다", 전부 실패하면 후보 선택 방향은 접습니다 (실행 중)

### 6. ⭐ A 재개는 0% — 연구의 두 번째 목표가 전혀 안 풀렸다

지금까지의 모든 실험 기록을 다시 집계하다가 발견했습니다. **B 를 끝낸 뒤 중단한 A 를 다시 시켰을 때:**

| 전략 | 물체를 어떻게 했나 | B 성공 | **A 재개 성공** | 재개에 걸린 스텝 |
|---|---|---|---|---|
| `flush` | 쥔 채 그 자리에서 전환 | 23 | **0% (0/23)** | **전부 300 (한도)** |
| `keep` | 〃 | 21 | 0% (0/21) | 전부 300 |
| `bon` | 〃 | 25 | 0% (0/25) | 전부 300 |
| `rtc` | 〃 | 13 | 8% (1/13) | - |
| `ret_pos` | 놓고 **위치만** 복귀 | 47 | 9% (4/47) | 300 |
| `retreat` | 놓고 **완전 복귀** | 64 | **62% (40/64)** | **중앙값 90** |

**"전부 300 스텝"이 핵심입니다.** 그 자리에서 전환한 경우 로봇은 A 를 **한 번도** 못 끝냈고, 매번 시간 초과로 끝났습니다. 되돌려 놓은 경우에는 90스텝(4.5초) 만에 해냈습니다.

**왜 이렇게 갈리나**

```
그 자리 전환:  A 물체를 쥔 채 B 를 하러 감
               → B 를 하려면 그리퍼를 열어야 함
               → A 물체가 **아무 곳에나** 떨어짐 (측정: 전환 시점보다 평균 6cm 낮은 곳)
               → A 를 다시 시켜도 그 낯선 배치에서 시작 → 학습 분포 밖 → 못 함

되돌려 놓기:   A 물체가 **원래 자리**로 감
               → A 를 다시 시키면 사실상 **에피소드 처음과 같은 상태**
               → 정책의 원래 실력(74~90%)이 그대로 나옴
```

- B 는 끝까지 유지됐습니다 (`b_still_satisfied_at_end` 22/23) — B 를 망친 게 아니라 **A 를 못 하는 것**
- `ret_pos`(9%) 와 `retreat`(62%) 의 큰 차이도 같은 이유로 보입니다: 손목 회전까지 되돌려야 물체가 제대로 놓입니다

**이게 `rollback` 을 만든 결정적인 이유입니다.** 초기 자세로 가지 않으면서 물체는 집었던 자리에 놓으므로, **제약을 지키면서 A 재개가 가능한 유일한 후보**입니다. (참고: [SwitchVLA](../02_논문노트/SwitchVLA.md) 는 rollback 으로 A 를 **되돌려 없애고** 재개는 다루지 않습니다. [기억 벤치마크들](../02_논문노트/기억과_재개_조사.md)도 재개를 다루지 않습니다.)

### 7. 로봇은 물체를 "안 놓아서" 실패하는 게 아니다

전환 후 B 구간에서 그리퍼가 한 번이라도 열렸는지 궤적으로 확인했습니다 (그리퍼 qpos > 0.035).

| 전략 | 결과 | n | **물체를 놓은 비율** | 놓기까지 스텝(중앙값) |
|---|---|---|---|---|
| `flush` | B 성공 | 23 | **100%** | 66 |
| `flush` | B 실패 | 47 | **100%** | 49 |
| `keep` | B 성공 / 실패 | 20 / 50 | 100% / 100% | 66 / 55 |
| `bon` | B 성공 / 실패 | 24 / 48 | 100% / 98% | 66 / 46 |
| `rtc` | B 성공 / 실패 | 13 / 57 | 100% / 100% | 54 / 57 |

**성공이든 실패든 100% 놓습니다.** 즉 "하던 일에 집착해서 물체를 안 놓는다"는 설명은 **틀렸습니다.**
로봇은 2.5~3.3초 안에 물체를 놓고 새 일로 갑니다. 그런데도 B 를 못 끝냅니다.
(실패할 때 더 빨리 놓는 경향이 보이지만 유의하지 않습니다 — Mann-Whitney p = 0.12)

**이게 `rollback` 의 근거를 바꿉니다.**

| | 틀린 근거 | 맞는 근거 |
|---|---|---|
| rollback 이 필요한 이유 | ~~물체를 놓게 만들려고~~ (이미 놓음) | **어디에 놓는지**가 중요하다 |
| 무엇을 개선하나 | ~~B 성공~~ (❓ 확인 필요) | **A 재개** — 물체가 원래 자리에 있어야 다시 할 수 있다 |

로봇은 지금 **아무 데나** 놓습니다 (전환 시점보다 평균 6cm 낮은 곳). 그래서 A 재개가 0% 입니다.
rollback 은 **집었던 자리에** 놓습니다.

| 대기 스크립트가 스스로를 기다림 | `pgrep -f` 패턴이 **자기 명령줄**과도 일치 | 자기 PID 를 제외하거나 PID 목록으로 직접 확인 |
| 판정기가 "쓸모없다"는 결론이 애매함 | 한 상태에서 **실행한 동작 하나**만 관측 | 같은 상태를 저장/복원해 후보를 여러 번 굴리는 오라클 실험 |
| 오라클 실험이 중간에 죽음 | 로봇수트 스텝 카운터가 누적돼 horizon(1000) 초과 → `executing action in terminated episode` | 상태 복원 시 `inner.timestep = 0; inner.done = False` 도 함께 되돌림 |
| 연쇄 대기 스크립트가 엉뚱한 PID 를 기다림 | `pgrep -f` 가 쉘 래퍼까지 잡음 | 실제 스크립트 PID 를 확인해 하나의 체인 스크립트로 정리 |
