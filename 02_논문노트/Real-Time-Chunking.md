## 📌 쉬운 말 요약

**한 줄로**: 로봇이 동작 묶음(chunk)을 하나 다 실행하기 전에 다음 묶음을 계산할 때, **"곧 실행될 앞부분은 그대로 두고, 나머지만 그에 맞춰 새로 채우는"** 방법입니다. 그래서 묶음이 바뀌는 순간에도 동작이 끊기거나 튀지 않습니다.

**비유로**: 운전하면서 내비게이션이 새 경로를 계산할 때, 좋은 내비는 **"지금 달리고 있는 차선과 속도는 그대로 이어받고"** 그 뒤 경로만 바꿉니다. 나쁜 내비는 새 경로를 받자마자 갑자기 급핸들을 꺾게 만듭니다. RTC 는 좋은 내비입니다.

**학습이 필요 없습니다.** 이미 학습된 모델에 추론할 때만 적용합니다.

**우리 연구와의 관계**: 연구주제.md 에서 "가장 가까운 논문"으로 꼽았던 논문입니다. 지시가 바뀌는 순간에도 이전 동작을 이어받게 해서 **리셋 없이 매끄럽게 전환**하는 `rtc` 전략으로 구현했습니다.

## 1. 배경 — action chunk 와 그 문제

SmolVLA, π0 같은 모델은 동작을 **한 번에 여러 스텝(예: 50스텝) 묶음으로** 예측합니다. 이게 action chunk 입니다.

```
추론 1회 → [a1 a2 a3 ... a50]  → 그중 앞 10개 실행 → 다시 추론 → [b1 b2 ... b50] → ...
```

문제가 두 가지 생깁니다.

**문제 1: 멈춤.** 다음 묶음을 계산하는 동안 로봇이 기다려야 합니다. 모델이 크면 수백 ms 멈췄다 움직였다를 반복합니다 (stop-and-go).

**문제 2: 튐.** 멈추지 않으려고 계산 중에도 이전 묶음을 계속 실행하면, 새 묶음이 도착했을 때 **이전 묶음과 방향이 달라서 동작이 확 꺾입니다.** 두 묶음은 서로를 모르고 따로 뽑혔기 때문입니다.

```
이전 묶음:  ───────────╮
                       │  ← 여기서 새 묶음으로 갈아타면
새 묶음:              ╰──────  갑자기 꺾임 (jerk)
```

## 2. 핵심 아이디어 — inpainting 으로 보기

그림의 일부를 가리고 나머지를 채워 그리는 걸 **inpainting** 이라고 합니다. RTC 는 새 묶음 생성을 이렇게 봅니다.

```
시간 ─────────────────────────────────────────▶
이전 묶음의 남은 부분:  [■■■■■■■■■■□□□□□□]
                         ↑고정   ↑부드럽게 따라감   ↑자유롭게 생성
새 묶음:               [■■■■■■■■■■▒▒▒▒▒▒░░░░░░░░░░░]
```

- **앞 d 스텝 (■)**: 새 묶음이 계산되는 동안 **어차피 실행될** 부분 → 이전 묶음과 **똑같이 고정**
- **그다음 구간 (▒)**: 이전 묶음을 **점점 약하게** 따라가도록 유도
- **나머지 (░)**: 새로 자유롭게 생성

## 3. 작동 원리 — flow matching 안에서 어떻게 고정하나

SmolVLA 는 **flow matching** 으로 동작을 만듭니다. 노이즈에서 시작해 10단계에 걸쳐 조금씩 동작으로 다듬는 방식입니다.

```
노이즈 x(1.0) → x(0.9) → x(0.8) → ... → x(0.0) = 동작 묶음
```

RTC 는 **매 단계마다 보정**을 더합니다 (LeRobot `modeling_rtc.py` 에서 확인).

1. 모델이 지금 단계의 속도 `v` 를 예측
2. 그 속도로 끝까지 갔을 때의 예상 결과 `x1 = x - t·v` 를 계산
3. **이전 묶음과의 차이** `err = (이전 묶음 - x1) × 가중치` 를 구함
4. 가중치는 앞 d 스텝은 1, 이후 `execution_horizon` 까지 줄어들고, 그 뒤는 0
5. `v ← v - (guidance 세기) × 보정` 으로 속도를 고쳐서 이전 묶음 쪽으로 끌어당김
6. guidance 세기는 초반(노이즈가 클 때)엔 크고, 후반엔 작아지며 `max_guidance_weight` 를 넘지 않음

모델 가중치는 전혀 바꾸지 않고, **생성 과정만 조종**합니다. 그래서 학습이 필요 없습니다.

## 4. 실험 (논문)

- 추론 지연을 크게 줘도 성공률이 유지됨 → **지연에 특히 강함**
- 작업 처리량(throughput)이 크게 향상
- **성냥 켜기** 같은 정밀한 작업도 지연이 큰 상황에서 성공

## 5. 한계

- **전환(지시가 바뀌는 순간)을 겨냥한 방법이 아님.** 같은 지시 안에서 묶음을 이어붙이는 문제를 풂
- 이전 묶음을 따라가게 하므로, 지시가 바뀌었는데 **이전 동작을 너무 오래 따라가면** 반응이 늦어질 수 있음 → `execution_horizon` 을 짧게 잡아야 함

## 6. 내 연구와의 관계

### 참고해서 쓴 곳

- **`rtc` 전환 전략** (`switch_experiment.py --strategy rtc`)
  - 모든 묶음 경계에서 이전 묶음의 남은 동작을 guidance 로 줌
  - **지시가 바뀌는 순간에도** 같은 방식 적용 → 방향은 새 지시로, 동작은 끊김 없이
  - 옵션: `--rtc-horizon`(따라갈 길이, 기본 10), `--rtc-delay`(완전 고정 길이, 기본 0), `--rtc-guidance`(최대 세기, 기본 10)
- 구현 중 주의점: RTC 는 보정 계산에 **자동미분**을 쓰므로 `torch.inference_mode()` 안에서는 안 됨 → `torch.no_grad()` 로 바꿈. 이전 묶음은 **정규화된 값**으로 넘겨야 함

### 우리 기존 전략과 비교

| 전략 | 방식 | 한계 |
|---|---|---|
| `flush` | 남은 묶음 버리고 새로 | 방향이 확 바뀜 |
| `keep` | 남은 묶음 다 쓰고 새로 | 반응이 늦음 |
| `blend` | 두 묶음을 **바깥에서** 가중평균 | 두 동작의 평균이 이상한 동작일 수 있음 |
| **`rtc`** | 새 묶음을 **만드는 과정에서** 이전 묶음에 맞춤 | 모델이 스스로 일관된 동작을 만듦 |

`blend` 는 RTC 의 가장 단순한 근사입니다. 9/14 실험에서 blend 가 효과가 거의 없었는데(저크 8.6 vs flush 9.0), RTC 는 모델 안에서 이어붙이므로 더 자연스러울 것으로 기대합니다.

### ⚠️ 우리 실험 결과 (2026-09-17): 전환에서는 오히려 나빠졌다

전환 이후에만 RTC 를 적용해서, 4개 태스크 쌍 × 2개 전환 시점 × 10회 평가했습니다.

| | flush (그 자리 전환) | **rtc** |
|---|---|---|
| B 성공률 | 32% | **18%** |
| 들고 이동 중 전환 (4→7 / 8→7) | 70% / 60% | **20% / 10%** |
| 지시 무시 (B 도중 A 를 끝내버림) | 0회 | **4회 (6%)** |
| 저크 (작을수록 부드러움) | 9.6 | **6.0** ✅ |
| 우회 비율 (성공 시, 1=곧게) | 1.52 | **2.32** |
| 전환 직후 되돌아감 | 0.2cm | **1.8cm** |

**왜?** RTC 는 새 동작을 **이전 동작(A 를 하던 방향)에 맞춰** 만듭니다. 같은 지시 안에서는 그게 매끄러움이지만, **지시가 바뀐 순간에는 A 방향으로 계속 끌려가다가** 뒤늦게 꺾습니다. 들고 이동 중일 때 특히 나쁜 건, 그때 A 의 움직임이 가장 크고 뚜렷하기 때문으로 보입니다.

**교훈: "매끄럽다 ≠ 자연스럽다."** 사람도 일을 바꿀 때는 하던 동작을 끊고 방향을 바꿉니다. 전환 순간에는 이전 동작과의 연속성을 **낮추거나 끊는** 게 맞고, 새 일 안에서만 RTC 를 쓰는 게 나을 수 있습니다.

**후속 실험 `flush_rtc`**: 전환 순간엔 이전 동작을 버리고, 새 지시의 첫 동작 이후부터 RTC 로 이어붙였습니다.

| | flush | rtc | flush_rtc |
|---|---|---|---|
| B 성공률 | 32% | 18% | **17%** |
| 지시 무시 | 0 | 4 | **0** ✅ |
| 저크 | 9.6 | 6.3 | 7.0 |

지시 무시는 없앴지만 성공률은 그대로 낮았습니다 (flush 와 짝 비교 19 : 8, p ≈ 0.05). **B 안에서도 RTC 가 방해**가 된다는 뜻입니다.

**전환 없이도 확인**: 태스크 하나만 수행할 때 RTC 를 켜면 90% → 80% (짝 비교 3 : 8, p ≈ 0.23). 계속 방향을 조정해야 하는 접시 밀기에서 7 → 3 으로 가장 크게 떨어졌습니다.

**정리 — RTC 는 부드러움과 반응성을 맞바꾼다**

| 상황 | RTC 영향 |
|---|---|
| 평범한 수행 | 작은 손해 (90 → 80%) |
| 방향을 크게 바꿔야 하는 전환 | 큰 손해 (32 → 17%) |
| **추론 지연이 큰 상황** (논문의 목적) | **이득** (0.5초 지연에서 12 → 28%) |

### ✅ 공정한 재평가 (2026-09-18): 지연이 있으면 RTC 가 확실히 도움

추론 지연을 모사해서(요청한 동작이 L 스텝 뒤 도착) 다시 비교했습니다. 전환 없이 태스크 4개 × 10회.

| 추론 지연 | RTC 끔 | RTC 켬 |
|---|---|---|
| 없음 | 90% | 75% |
| 0.25초 | 72% | 72% |
| **0.5초** | **12%** | **28%** (짝 비교 6 : 0, p ≈ 0.03) |
| 1초 | 0% | 8% |

**논문 주장이 맞는 조건을 확인했습니다.** 지연이 없을 때의 손해와 지연이 있을 때의 이득이 뒤집힙니다. 다만 전환 상황(지연 0.5초, 잡은 직후)에서는 RTC 7% 로 keep 13% 보다 나빠서, **지연 대응 도구로는 맞지만 전환 도구로는 아니다**가 최종 결론입니다. → [지연 실험](../04_실습/05_libero/latency/README.md)

## 7. 용어

| 용어 | 뜻 |
|---|---|
| action chunk | 한 번에 예측하는 여러 스텝의 동작 묶음 |
| inpainting | 일부를 고정하고 나머지를 채워 생성하기 |
| flow matching | 노이즈에서 출발해 여러 단계에 걸쳐 데이터(동작)로 다듬는 생성 방법 |
| guidance | 생성 중간에 원하는 방향으로 끌어당기는 보정 |
| inference delay (추론 지연) | 입력을 받고 동작이 나올 때까지 걸리는 시간 |
| execution horizon | 이전 묶음을 따라가도록 유도하는 구간 길이 |
| throughput | 같은 시간에 끝낸 작업량 |
